# 0002. Authentication: magic link plus anonymous demo sessions

- **Status:** Proposed
- **Date:** 2026-10-27
- **Deciders:** Sampson (`Yine-Eng`)

## Context
Students should be able to sign in without passwords. Judges must be able to try the product in one tap without signing up. BSU SSO integration is out of scope for the competition timeline.

## Decision
- **Supabase Auth email magic link** for real users, using the `@supabase/ssr` cookie-based session pattern with session refresh in middleware.
- **Supabase anonymous sign-in** only for "Explore as Veronica". Anonymous users get `profiles.is_demo = true` and are purged after 24 h.
- Roles live in `profiles.role` (`student | mentor | staff | admin`), default `student`. Column-level grants stop users changing their own role. An admin-only RPC changes roles and writes the audit log.
- Optional email-domain allowlist via `AUTH_ALLOWED_EMAIL_DOMAINS`.
- Supabase's built-in SMTP has a very low hourly limit, so a free-tier transactional email provider (e.g. Resend) should be configured as custom SMTP before the pilot.

## Consequences
- No passwords to store or reset.
- Demo users use exactly the same code paths and RLS policies as real users.
- Magic-link deliverability depends on the SMTP provider. University mail filters should be tested early.
- Anonymous sign-in must be rate-limited (Supabase limits plus our own per-IP limiter) to prevent database bloat.

## Alternatives considered
- **Password auth:** more support burden and weaker security in practice.
- **Google OAuth:** a good addition later if BSU uses Google Workspace.
- **Client-only demo with mock data:** zero backend cost, but different code paths would let bugs hide in the real flow.
